# Shipping

The submission checklist. `PLAN.md` §5 Phase 9 is eight bullets; this is the
step-by-step, and it exists because there was no submission procedure anywhere.

| App | Bundle | ASC ID | After 3.0 |
|---|---|---|---|
| Numeriqo | `de.kaikunze.numeriqo` | 6749287069 | Free + one IAP |
| Numeriqo Pro | `de.kaikunze.numeriqopro` | 6751394841 | Same build, unlocked, removed from sale |

## 1. The blocker: create the in-app purchase

**Nothing else matters if this is skipped.** `de.kaikunze.numeriqo.full` exists
only as a local `.storekit` fixture for the simulator. Until it exists in App
Store Connect, StoreKit returns no product, the price never appears, and
"Unlock everything" reports that the store is unavailable. Every paid feature is
unreachable and a reviewer will find it.

In App Store Connect, on **Numeriqo** (6749287069):

- Type: **non-consumable**
- Product ID: `de.kaikunze.numeriqo.full`
- Reference name: `Numeriqo Full`
- Price: **$4.99** (tier matching Just Kakuro)
- **Family Sharing: on**
- Display name: `Numeriqo Full`
- Description: *Every lesson, every drill, teaching hints, large grids and stats.
  One purchase, forever.*
- Upload a review screenshot (the paywall will do).
- **Attach it to the 3.0 version** so it is reviewed with the build. An IAP
  submitted on its own sits in "Waiting for Review" indefinitely.

Verify afterwards by running the app against the real sandbox and checking the
price appears on the paywall button. If it says "The App Store hasn't sent a
price yet", the product is not live to StoreKit.

## 2. Metadata

Copy is drafted in `STORE.md`: subtitle, keywords, promotional text,
description, What's New for each SKU, and the App Review notes. Two things it
cannot supply because they do not exist yet:

- **Privacy policy URL** (required). The app collects nothing, so the policy is
  short, but the URL must resolve.
- **Support URL** (required).

Also set: age rating, copyright, and category (Puzzle). The App Privacy answers
must be **Data Not Collected**, which is what `PrivacyInfo.xcprivacy` declares.
Any other answer contradicts the manifest.

## 3. Screenshots

`build/screenshots/` holds both required sizes, generated by:

```bash
for ID in <iPhone 16 Pro Max udid> <iPad Pro 13-inch M4 udid>; do
  xcodebuild test -project Numeriqo.xcodeproj -scheme Numeriqo \
    -destination "platform=iOS Simulator,id=$ID" \
    -only-testing:NumeriqoUITests/DesignShotTests
done
```

iPhone 6.9" and iPad 13" are the only two sizes App Store Connect still
requires; everything else is scaled from them. Order and rationale in
`STORE.md`.

## 4. Build and upload

```bash
xcodebuild archive -project Numeriqo.xcodeproj -scheme "<SKU>" \
  -configuration Release -destination 'generic/platform=iOS' \
  -archivePath "build/<SKU>.xcarchive" -allowProvisioningUpdates

xcodebuild -exportArchive -archivePath "build/<SKU>.xcarchive" \
  -exportOptionsPlist ExportOptions.plist -exportPath "build/export-<SKU>"
```

Both SKUs archive and export cleanly. Check the exported `.ipa` before
uploading: no `.storekit` fixture, no `*.debug.dylib` or `__preview.dylib`,
`PrivacyInfo.xcprivacy` present, `ITSAppUsesNonExemptEncryption` false.

`CURRENT_PROJECT_VERSION` is the build number and must increase for every upload
against the same `MARKETING_VERSION`. It is currently `1`, correct for the first
3.0 build.

Upload with Transporter or `xcrun altool --upload-app`, which needs an App Store
Connect API key. That step is yours; nothing here uploads.

## 5. Order of operations

`MONETIZATION.md` §3 is binding on this:

1. Ship 3.0 to **both SKUs simultaneously**.
2. Then set Numeriqo Pro to **removed from sale**. Existing owners keep it, can
   re-download it, and keep receiving updates.
3. Keep shipping Pro builds. One extra archive per release.

**Do not delete the Pro app.** Deleting it strands paying customers, which is
the exact thing the `NUMERIQO_PRO` flag exists to prevent.

## 7. Known gaps, shipping anyway

Recorded so they are decisions rather than surprises. None blocks review.

- **Sound is not implemented.** `DESIGN.md` §6 specifies it; it is not built
  because it cannot be evaluated here.
- **Increase Contrast is not implemented.** Light/dark, Dynamic Type and Reduce
  Motion are.
- **The parity drill does not force a parity deduction.** Parity is unreachable
  in generated boards, which `TECHNIQUES.md` argues is the correct outcome.
- **About 28% of daily puzzles grade off the advertised Steady band**, because
  the generator takes the nearest match after six attempts rather than looping.
- **A daily whose seed failed to generate would retry the identical seed**, so
  it would fail identically for everyone on that date. Probed across the next
  730 days with zero failures, but nothing prevents it.
